- Added `ScreenTracker` (builder, reviewed): between marker sightings it follows the screen with optical flow. In overlay mode it tracks only static regions (marker windows + bezel ring) so scrolling/video can't drag it; it masks out the hand, has sanity checks (convex, area ±30%, in-frame) and takes ~5 ms/frame. Synthetic tests: scrolling 3.2 px, 100 noisy frames all within 8 px. Not yet tested live.
- Touch detection: `tap_probe.py` showed the mic mostly misses screen taps (3/10) while the motion sensor catches them but also fires on typing. Design: motion-sensor tap (`imu_taps.py`) + camera gate (fingertip still on screen), built by the builder; the user reports tapping "does work nicely".
- Marker robustness (builder, verified): sub-pixel corners (overlay error 4.6 → 1.7 px), guided 2x re-detection of missing markers (~1 ms/frame), and trust rules so a noisy 2-marker diagonal fit can't override good tracking. The live failure (only 2 of 4 markers decoding) did not reproduce in synthetic frames; real frames are needed to tune it.
- Touch review (11 findings) fixed and verified: stale taps dropped before deciding, 0.4 s refractory + min click gap, touch only with a fresh screen M, ≥3 samples (5 was impossible at 15 fps), monotonic clock (sensor timestamps), bounded/validated UDP input, clear port error. imu_taps.py is now stdlib + macimu only and runs as a root-owned copy under /usr/bin/python3 (setup in README).

## 2026-11-12
- Touch mode now behaves like a touchscreen: hovering doesn't move the cursor, only taps click. imu_taps default k=3 (user-tested: catches light taps).
- **Background streaming works:** GlassesCamBT uses VideoCodec.hvc1 + a VideoToolbox decoder (from Meta's newer sample, software fallback in background, CPU CIContext). Measured ~14 fps for 75 s straight while the user switched apps and locked the phone. Frames arrive at 504x896 (one ladder step below raw's 720x1280).
- Occasional lag remains; likely Bluetooth bandwidth, the ~100 ms Wi-Fi round trip, and HEVC keyframe waits. Not measured yet.
- Decoder review (12 findings) fixed: software decoding always (as in Meta's sample), all VideoToolbox work on one serial queue, nil output counts as failure, backoff + cap on recreation, output stalls after 2 s without a fresh frame, one latest-frame slot for main, reset on stop. Live recheck: full 720x1280 again, ~13-14 fps for 75 s with app backgrounded/locked; typical longest gap per 5 s 200-400 ms, worst 879 ms. Frames arrive in bursts (Bluetooth), which is the remaining lag.
- Touch debugging: --touch-debug logs every tap decision plus a per-second stats line to build/touch_debug.log. A live session showed the helper delivers all taps (peaks 6–56, so light taps are felt); the tracker rejected them because it had no fingertip samples around the tap (n=0 within ±0.5 s). Cause (hand not detected vs processing lag) still to be measured with the stats line.
- Touchscreen gestures (builder, reviewed): tap = click, one-finger move = drag, two-finger move = scroll. The reviewer found run() discarded every action from engine.frame() (clicks lost ~50%, drags truncated, button left held); fixed via a tested touch_step(), plus button-safety (tick, stall release, release in finally), consistent tap/drag thresholds (30 pt), burst-tolerant lift-off, majority two-finger vote, scroll deadband. 400/400 simulated taps click once. Network reads now time out after 3 s (was 30 s), verified with a hung local stream.
- Control panel (builder, security-reviewed): `GlassesTouch.command` opens a local web panel (glasstouch/panel.py, stdlib, 127.0.0.1:8765) with phone address, live preview, switches, Start/Stop, status and log. The root tap helper is now a LaunchDaemon installed by `sudo ./install_helper.sh` (staged copy, re-verified, no symlinks/FIFOs, atomic swap). Tracker releases the mouse and exits on SIGTERM/SIGHUP or when its parent dies (watchdog). Panel and tracker tests pass; the real sudo install and a live panel run are untested.
- Live panel session: taps mostly rejected (`moving` 35–130 pt from the tap's approach/withdrawal, `few-samples n=2` at 13 fps) and the screen tracker drifted (fingertips mapped to y≈2300) because 2-marker fits that disagreed with a drifted tracker were always rejected. Fixed (builder): tap = fingertip at the tap instant (interpolated, ≥1 on-screen sample within ±0.12 s); one-finger drag needs a 0.35 s hold first (a tap's withdrawal is a click); 3 consistent 2-marker fits override the tracker; tracking-only M expires after 8 s. Tests pass; not yet retested live.
- **Marker detection root cause found** (206 recorded glasses frames): markers 0 and 2 were found as candidates and their cells read perfectly at cell centres, but the detector's default bit sampling (0.13 cell margin, 4 px/cell) let blur from neighbouring cells flip bits at ~32 px. Setting perspectiveRemoveIgnoredMarginPerCell=0.3 and perspectiveRemovePixelPerCell=8 raised frames with 2+ markers from 44 to 195 of 206 (all four ids ~80%), all-4 fit residuals ≤3.1 px, 6 ms/frame. Guided re-detection still adds markers (70 in 82 partial frames). Regression test uses 4 real frames in glasstouch/testdata (screen content blurred); it fails with the old settings.
- Live retest after the marker fix: **86 of 96 taps clicked (90%)**, 0 no-samples, markers in almost every frame, 34 drags each with one release. The rest: Dock/edge taps mapped 5–50 pt below the screen (now accepted within EDGE_TOL = 60 pt and clamped 1 pt inside, via tested screen_point(); this also fixed drag clamping onto FailSafe corners) and hand-on-keyboard taps at y≈2400 (correctly rejected).
- Panel now shows the tracker's annotated view (tracker --view-port 8767 --no-window; no OpenCV window). imu_taps sends gyro/accel-axis/lid features per tap and the tracker logs them with hands= (MediaPipe now tracks 2 hands, pointing hand = nearest previous fingertip), to find a screen-tap signature that rejects typing and bumps. Needs the helper reinstalled.
- False-touch filters: taps need acc_peak ≥ 0.004 g (panel "Tap strength", --tap-min-acc), knocks (> 0.08 g or gyro > 3) and taps while a second hand is over the keyboard are rejected. Gyro turned out useless for screen taps (stuck at bias ~0.5); the lid sensor reports nothing. Replaying the 90 s recording at 0.004: first segment (screen taps) 20/21 pass, the low-strength runs 1/24, 7/24, 0/10 pass, all 3 knocks rejected. Not yet retested live.
