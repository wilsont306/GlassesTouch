# Known issues and gotchas

- pyautogui FAILSAFE fires at all 4 screen corners. `map_point` clamps to [1, W-2] x [1, H-2] so the tracker never parks the cursor on a corner.
- On macOS, `pyautogui.moveTo` sends plain mouse moves, not drags. While pinched, use `dragTo(..., mouseDownUp=False)`.
- `--region` units (Retina points vs pixels) are unverified. If the capture is offset, try halving or doubling the values.
- With a free Apple ID, an app installed on the iPhone stops opening after 7 days. Rebuild it to reinstall.
- On macOS, git and xcodebuild both refuse to run until the Xcode license is accepted (`sudo xcodebuild -license accept`).
- The `reviewer` agent didn't use `glasstouch/.venv` and so assumed the dependencies were missing. Tell it to use `.venv/bin/python`.
- A free (personal) Apple team can't sign the Hotspot Configuration or Access Wi-Fi Information capabilities, so both were removed from `CameraAccess.entitlements`. Meta's docs say Wi-Fi camera streaming needs Hotspot, but another page says streaming runs over Bluetooth Classic. Tested 2026-11-11: it does NOT work. Preview hangs, and the phone log shows `NEHotspotConfigurationHelper failed to communicate to helper server` each time Preview is tapped (the SDK tries to join the glasses' Wi-Fi). Live streaming with SDK 0.6.0+ on iOS needs a paid Apple Developer Program membership. **Workaround (works, tested 2026-11-11):** `GlassesCamBT/` is Meta's CameraAccess sample at SDK 0.5.0 (main commit 28a81e1), which streams over Bluetooth with no Hotspot entitlement. Risk: newer glasses firmware could stop accepting 0.5.0 at any update.
- The 0.5.0 sample ships with manual signing on Meta's team (V9WTTPBFK9, "Facebook Generic" profile). Switch to automatic signing with your own team.
- `xcodebuild -destination 'id=<phone>'` fails with a "My Mac" error while the phone is locked or "unavailable". Unlock it, or build with `generic/platform=iOS` and install with `xcrun devicectl device install app`.
- Live stream quality is well below on-glasses recordings: Bluetooth bandwidth forces per-frame compression (Meta docs), and the resolution ladder drops 720x1280 to 504x896. Lower fps gives sharper frames; GlassesCamBT now asks for 15 fps and sends JPEG at 0.85.
- `--show-markers` overlay: the windows exist on screen, but the tracker's own screenshot check needs Screen Recording permission; the camera test doesn't.
- Real cursor control needs macOS Accessibility permission for the app that runs the tracker (Terminal, or Claude when using its terminal pane); without it pyautogui fails silently. tracker.py now exits with a clear message when the permission is missing (dry-run excepted).
- Never run `sudo .venv/bin/python imu_taps.py`: the venv, the script and Homebrew's Python are user-writable, so that is a local privilege-escalation path. Use the root-owned copy in /usr/local/libexec/glasstouch with /usr/bin/python3 (root-owned Xcode Python), per README. Re-copy after editing imu_taps.py.
- Touch has no contact check: a still fingertip on the screen plus any knock to the laptop counts as a touch.
- Touch thresholds must fit the frame rate: the tap window (-0.15..+0.10 s) holds only 3-4 frames at 15 fps, so TOUCH_MIN_SAMPLES=5 made every tap fail silently (fixed: 3). Spread limit raised 25 → 40 pt because the tapping motion moves the fingertip. Re-tune if the fps changes.
- Threat model (accepted for a single-user Mac on a trusted network): the panel token stops web pages (CSRF, DNS rebinding) but not other local accounts or local processes; the phone's MJPEG stream and the tap datagrams on 127.0.0.1:9787 are unauthenticated, so someone on the same Wi-Fi or the same Mac could inject frames or taps. Fixing this needs authenticated transport end to end.
- install_helper.sh runs whatever is in the repo as root at the moment you run it: only run it on code you trust.
- ArUco at ~32 px: the default perspectiveRemoveIgnoredMarginPerCell (0.13) misreads thin-celled ids (0, 2) under blur. Keep 0.3 / 8 px per cell (tracker.make_marker_detector). Synthetic blur tests did not reproduce this; only real frames did.
- The panel's tracker view (127.0.0.1:8767, MJPEG) shows the camera image, including your screen. It's local-only with a Host check: other web pages can embed but not read it, but any local process on this account can.
- The glasses' capture button can't be read with DAT 0.5.0 and doesn't interrupt the stream (Inputs exist only in DAT 1.0, experimental, which needs a paid Apple account for streaming).
- A 3-marker homography can absorb one partly-occluded marker's uniform corner shift without a visible reprojection error; that's why covered markers are dropped by hand position instead of by geometry checks.
- two_finger() gives false positives on one-finger poses seen from the glasses (2D wrist/PIP distances, no perspective). Gestures no longer let it turn drags or withdrawals into scrolls; scrolling needs two fingers moving right after a single touch.
- Calibrating a fixed fingertip offset from calibrate.html made live taps worse; per-tap scatter (20–50 pt) dominates, and the bias probably depends on hand approach. Don't re-apply a shift without a live A/B check.
- Pairing opens a listener on the Mac's Wi-Fi address for up to 120 s that accepts one POST /pair with a 128-bit one-time code; anyone who sees the QR in that window could pair their own address (then feed frames, as the existing threat model already allows). It closes on success, cancel, expiry or panel exit.
- No iOS simulator runtime is installed, so phone UI changes can only be checked on the device.
- Panel SVG: never put a stroke (even with vector-effect="non-scaling-stroke") on a `<use>` of the unit lens path scaled to frame size; Chrome paints it over the whole page. Fills on scaled `<use>` are fine; strokes need real-coordinate paths (generated from the unit path).
- Panel CSS: unhiding an element restarts any CSS animation on it; keep load-time fades off elements that get toggled (the QR wrapper).
- Frame capture times assume the phone's and the Mac's clocks are both set automatically (NTP, typically within tens of ms). If they are seconds apart the tracker says so once and falls back to the fixed --camera-latency guess. --link-latency (0.1 s) is a guess for the glasses-to-phone minimum delay; fit it from live sessions.
- MediaPipe resizes the hand to a fixed input either way, so the crop mostly helps *finding* the hand (the palm detector sees it larger), not landmark precision. Judge it by hand=N/frames in the stats line with and without --no-hand-crop.
- pyautogui.doubleClick on macOS posts two plain clicks without kCGMouseEventClickState, so apps (browsers' dblclick, the Finder) see two single clicks. tracker.double_click posts the second press through Quartz with click state 2 (the first tap's click is the first press; until 2026-11-24 it posted a whole 1,1,2,2 pair, so apps saw three presses per double-tap). Earlier "N double-clicks" counts came from the tracker log, not from apps.
- Content matching needs Screen Recording permission for Terminal (or whatever runs the tracker); macOS gives apps without it only the wallpaper and menu bar. It also weakens on plain screens (a blank white page, a solid fill): too few features, so it returns nothing and the markers or tracker carry on. Screen content that changes faster than the 1 s screenshot refresh (video, fast scrolling) matches less well.
- An .app whose executable is a shell script can be started under Rosetta on Apple Silicon. An exec'd arm64 binary still runs native, but the Intel preference passes to every program it spawns: `uname -p` says i386 and rubicon-objc (pyautogui) crashes on `objc_msgSendSuper_stret`. GlassesTouch.app's launcher is therefore a compiled program (make_app.sh builds it with clang), not a script.
- In a PyObjC app, Python signal handlers don't run while Cocoa's run loop is idle; app.py keeps a 0.5 s no-op NSTimer so SIGTERM/SIGINT quit it.
- macOS files a privacy permission under the program an app starts as. With a bash-script launcher GlassesTouch.app was listed under Accessibility as "bash" (/bin/bash), so turning it on would have let any bash script launched as an app control the computer. The launcher is now a compiled program signed as local.glasstouch.panel that execs the .venv Python; the tracker then reported "GlassesTouch" as missing the permission, but which name macOS lists is still to be confirmed by the user. The signature is ad hoc, so a rebuild that changes the launcher, Info.plist or icon may make macOS ask again.
- OpenCV's macOS camera backend opens every camera with the session preset Medium (about 480x360) and never changes the device format; CAP_PROP_FRAME_WIDTH/HEIGHT snap back to the current format. tracker.py (maccam.use_best_format) switches the opened camera to its largest format up to 1920x1440 at 24+ fps (the iPhone: 1920x1440 at 60, its 4:3 whole-sensor view) and keeps the device locked for configuration, because macOS restores the preset's format when the lock is released. The tracker logs "frames arrive at WxH" once per run to confirm it took. Through Continuity Camera the Mac gets only the iPhone's main lens (no telephoto, no 0.5x except via Center Stage/Desk View), so any zoom from the Mac side is digital.
- AVFoundation is loaded through objc.loadBundle without PyObjC's AVFoundation metadata, so methods with an NSError** out-parameter return a bare BOOL (lockForConfiguration_ -> True), not (BOOL, error); maccam accepts both. Live, unpacking a pair crashed the tracker at start.
- Camera sources: OpenCV numbers Mac cameras by joining AVCaptureDevice devicesWithMediaType video and muxed and sorting them by uniqueID (NSString compare:), not in the system's order; the panel lists them the same way. Live, before that sort, choosing the iPhone opened the MacBook camera (iPhone id 158F... sorts before 6C70...). A different OpenCV build that enumerates differently would open the wrong camera again; the tracker log's markers=0 with hands in every frame is the tell. Continuity Camera devices are listed as AVCaptureDeviceTypeExternal there. Homebrew's Python.app has no camera usage string; GlassesTouch.app's Info.plist has one, but which bundle macOS checks for the app's process (see the Python.app note above) is unconfirmed.
- Free-team provisioning profiles last 7 days, and Xcode deletes the expired one at the next build; xcodebuild -allowProvisioningUpdates then fails with "No Accounts" unless an Apple ID is signed into Xcode (Settings > Accounts). The installed phone app also stops opening when its profile expires.
- The phone app keeps "linked" from its last pairing (UserDefaults) even after the Mac switches to another source (picking a camera in the panel); only a new Pair phone points the Mac back at the phone. The phone camera view shows whether the Mac is actually reading instead.
- A newly signed free-team build can't install until the phone is registered: build once with -destination id=<UDID> -allowProvisioningDeviceRegistration while the phone is unlocked, then trust the developer under Settings > General > VPN & Device Management on the phone.
- Changes to panel.py or app.py (endpoints, the tracker launch) only take effect after quitting and reopening GlassesTouch; page changes (panel.html) reload by themselves.
- A script error in panel.html stops the whole page script, including the poll that auto-reloads it, so a half-applied edit can leave the open window stuck on a broken page until GlassesTouch is reopened. Apply multi-part page edits in one write.
- Without markers, content matching has little to match on plain pages (the tutorial's grid, blank windows): the screen tracker holds it for a while, then it is lost. Screen markers on, or on-demand markers (not built), cover it.
- Content matching at fastThreshold 6: the synthetic whole-screen test's worst error rose from 2.6 to 5.1 pt (limit 6); watch for click offsets when the screen is found from content.
- The installed app runs the copy in ~/Library/Application Support/GlassesTouch, not this folder: code changes show only after `./make_app.sh` (then reopen the app), and its logs are in build/ there (tracker.log, touch_debug.log), not in the project's build/. The copied .venv points at Homebrew's python@3.12; upgrading or removing that breaks the app until the .venv is rebuilt and make_app.sh rerun.
