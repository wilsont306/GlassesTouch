# Decisions

- **Video path: a phone app using Meta's DAT kit, not a web app.** Per Meta's docs, only the Device Access Toolkit can use the glasses' camera. Glasses Web Apps run only on Ray-Ban Display glasses and have no camera access. A WhatsApp or Messenger video call plus `--region` screen capture is the fallback that needs no code.
- **Start from Meta's CameraAccess sample** instead of writing a new app.
- **Use SDK 0.5.0 (`GlassesCamBT/`) for now:** it's the last version that streams over Bluetooth, which works on a free Apple account. Move to 1.x (`GlassesCam/`) if a paid membership is added or 0.5.0 stops working.
- **Screen location from 4 printed ArUco markers** (DICT_4X4_50, ids 0–3 = TL, TR, BR, BL) and a per-frame homography.
- **On-screen overlay markers (`--show-markers`) instead of printed ones:** exact known positions, no printing; any 2 markers suffice (corner-based RANSAC homography).
- **Track only static screen regions between marker sightings** (marker windows + bezel), because tracking the whole screen follows scrolling content.
- **Touch = camera for *where*, tap sensor for *when*:** a single camera can't tell touching from hovering. Choosing between mic and motion sensor by experiment (`tap_probe.py`).
- **Click by pinch with hysteresis** (enter below 0.30, exit above 0.45). The DAT experimental Inputs module (capture button or touchpad) is a possible, more reliable alternative.
- **Developer Mode in the Meta AI app** for testing; Developer Center release channels are only needed for sharing.
- **hvc1 codec on the phone** so the stream keeps running with the app backgrounded or the phone locked; costs one resolution step (504x896).
- **Touch mode = touchscreen semantics:** no hover cursor; click only on camera-gated motion-sensor taps.
- **Touchscreen gestures (user choice):** one finger: tap = click, touch-and-move = drag; index+middle together: touch-and-move = scroll (like a Mac trackpad). Touch-down comes from motion-sensor taps; lift-off must come from the camera (finger stops, leaves the screen or the hand pulls back), so gesture ends are heuristic.
- **Local web panel instead of a native app:** stdlib-only, launched by a .command file so the tracker inherits Terminal's Accessibility permission; the root helper runs as a LaunchDaemon so nothing needs sudo per session.
- **Hold-to-drag:** one-finger drag = touch, hold 0.35 s, move (click, then down/moves/up), because the withdrawal after a tap looks like movement to a single camera. Two-finger scroll starts immediately. Clicks land ~0.35 s after the touch.
- **Gestures v3 (replaces hold-to-drag):** tap = click immediately; drag = double-tap-and-drag (second tap 0.4–0.9 s after a click, within 60 pt, then move); two fingers = scroll, ending as soon as the pose breaks or the fingertip leaves the screen. Reason: with no lift-off sensor, "tap, rest, pull away" looked like hold-then-drag and produced phantom drags; a second sensed tap can't be faked by pulling away. Taps < 0.4 s apart are dropped as ringing (helper refractory and TOUCH_MIN_GAP), hence the 0.4 s lower bound.
- **(Reverted: the shift felt "a lot worse" live, TIP_DY = 0.) Calibration = a constant fingertip shift (TIP_DY), not a fitted warp:** one session's 10 points gave 54 → 43 pt with a shift and 38 pt with an affine; the remaining error is scatter, so the extra parameters would mostly fit noise. Re-run calibrate.html if the glasses fit or seating position changes.
- **Connect the phone by QR pairing, not Bonjour or USB:** this Wi-Fi blocks multicast (a Bonjour scan saw only the Mac), and a cable would have to stay plugged in. The phone scans a code from the panel and POSTs it to a short-lived listener; the Mac uses the request's source address, so nobody types or sees the IP. The iPhone Camera opens the app via the existing `cameraaccess` URL scheme, so the app needs no scanner of its own.
- **Frame timing from the glasses' own timestamps**, sent by the phone as X-Capture-Time, instead of arrival time minus a fixed latency: Bluetooth delivers frames in bursts (gaps up to ~0.9 s), so arrival time put the fingertip at the wrong moment of a tap. The tracker reads MJPEG itself because OpenCV/FFmpeg drops multipart headers.
- **Drag = double-tap, rest, slide** (refines gestures v3): movement within 0.2 s of the second tap is the finger lifting off and gives a double-click; a camera alone cannot tell lift-off from sliding, but lift-off starts immediately and a deliberate drag doesn't.
- **Six overlay markers** (corners + left/right edge midpoints) instead of four: a fit needs any 2, and with corners only, looking at part of the screen often showed fewer.
- **Find the screen from its own content** (screenshot + ORB + homography) as the fallback when markers are too few, instead of more markers or screen-edge detection: the Mac knows exactly what it displays, any visible part of the screen gives a fix, and ORB is fast enough per frame (SIFT is more accurate but 5-10x slower). Markers stay the primary source.
- **A drag drops at its first pause** (under 150 pt/s for ~3 frames), because the camera can't see the finger leave the glass and the pull-away looks like more dragging. Very slow, careful drags end early; keep moving or drag again.
- **No typing veto.** Rejecting taps while a second hand was over the keyboard cost far more real taps than it saved (41 in one session once the hand crop found resting hands reliably); typing taps are already rejected as off-screen because the pointing finger is on the keyboard. Remaining risk: a finger held still on the screen while the other hand types can turn a keystroke into a click.
- **The panel shows the raw camera footage** (user), not the tracker's annotated view; the HUD readouts carry the status.
- **Drag = tap, hold 0.15 s (was 0.3, then 0.2; user: felt long), slide** (user), replacing double-tap-and-drag; double-tap is just a double-click. A slide must continue over two frames, so a one-off jump of the fingertip estimate can't start a drag. Phantom drags from a resting finger pulling away are possible again, but the drop-at-pause rule ends them within ~0.15 s.
- **Lift-off from hand size, not speed:** a finger lifting off the glass brings the hand toward the eye, so it looks bigger on the screen plane; sliding keeps it the same. Speed alone couldn't tell a slowdown from a stop before a lift. The speed rule stays as a slow backup.
- **A scroll scrolls one way: its first stroke's direction.** The camera can't see the fingers leave the glass between repeated strokes, so return strokes would scroll back; ignoring motion against the first stroke makes repeated strokes work like on a trackpad. Changing direction needs a new two-finger touch.
- **Drag lift-off = pause then turn** (from 24 live pauses: carrying on turned under 20 deg, pull-aways over 50): the hand-size cue stays but rarely fires (hands grew at most 8 % when lifting).
- **The Mac app is installed, with its code beside it, not a standalone bundle.** make_app.sh puts GlassesTouch.app in /Applications and copies glasstouch/ and its .venv to ~/Library/Application Support/GlassesTouch (settings and logs in build/ there, the same layout as the project, so no Python path changes). The bundle holds only a launcher with no paths compiled in, the icon and Info.plist: reinstalling gives the same ad-hoc signature (CDHash checked across two builds), so macOS keeps the permissions; code inside the bundle would change the signature on every code change. Still no py2app/PyInstaller (hundreds of MB with MediaPipe and OpenCV, and the tracker and overlay re-run sys.executable as child processes) and no Electron; the cost is that it needs Homebrew python@3.12 (the .venv's base) and runs only on this Mac. Replaces "a thin window over the project, run in place" (user: an actual application, not one in the project folder).
- **A camera pointed at the screen = a camera the Mac sees** (built-in, USB, an iPhone through Continuity Camera), not a camera mode in the phone app: the tracker already read Mac cameras by number, so it was a panel change with no iOS build, and local cameras lag less than Wi-Fi MJPEG. Limit: an iPhone only appears with the same Apple ID as the Mac. Saved by the camera's uniqueID, not its number, because numbers shift when cameras connect or disconnect.
- The panel page is a file (glasstouch/panel.html), read per request, and the open page reloads itself when the file's change time moves (reported in /status): page edits show in the running app without a restart. Python changes (panel.py, app.py) still need quitting and reopening GlassesTouch.
- **On-demand markers** over always-on or off: hidden while content matching finds the screen, shown when it is lost; the hide check ignores the marker windows so the markers cannot keep themselves hidden-then-lost. Default for new settings.
- **Textured tutorial stage + ORB fastThreshold 6** instead of markers in the tutorial: the plain grid cannot be found by content matching at any threshold; a visible but faint camouflage at 22 % (the faintest that held in simulation) plus the lower threshold can. Lower threshold costs ~2x match time.
